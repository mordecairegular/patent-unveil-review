# 技术交底书生成模板（Step 7）

详细章节范例与 **mermaid** 图示模版见同目录 **`template_reference.md`**。

## 7.1 章节结构

### 主流程章节结构（工程方法 / 软件系统 / 数据处理 / 控制测算）

```
注意事项
一、技术背景与现有技术
   （一）现有技术（按技术方向分类，含专利检索结果）
   （二）现有技术存在的缺点
二、本发明所要解决的技术问题
三、本发明技术方案的详细阐述
   （一）方案背景
   （二）系统框图（**mermaid**，如 `flowchart` + `subgraph` 分层；交付前经工具转 PNG；**不要** ASCII 文字框图）
   （三）模块功能说明（说明各模块的**作用、输入、处理依据（规则/模型/阈值/映射/约束）、输出**及与上下游模块的关系；**避免只写"用于识别/判断/优化/修正"的功能性描述**）
   （四）系统流程说明（**mermaid 流程图**，交付前经工具转 PNG；**不要** ASCII 文字/箭头流程图）
   （五）符号与公式（出现公式或形式化变量时**须设**；**须**先符号与变量定义、再写公式；体例见 **§7.7** 与 **`template_reference.md`**）
   （六）关键技术参数（参数表「符号」列与符号表 **同形**）
四、与现有技术相比，本发明具有哪些优点？
五、本发明的技术关键点和欲保护点是什么？
六、其它
   （一）实施例（具体实施方式、技术效果、参数示例）
   （二）可替代实施方式与规避设计防御（核心特征的替代实现方向与对竞品回避设计的覆盖说明，2–3 条即可；素材可来自窄化备选与从属保护点分析，不强制展开）
   （三）术语与缩略词表（专用名词/英文缩略词/英文全称/中文含义；全文符号与叫法以此为准）
   （四）引用文献表（现有技术与背景引用的公开号/文献标识与标题；URL 与来源状态仍留证据包，不入正文）
```

**本发明摘要（固定栏目，不占章号）**：「注意事项」之后、第一章之前设「**本发明摘要**」段：300–500 字概括技术问题、核心方案主线与主要技术效果；可直接复用 Step 6（确认点 4）经用户确认的预览概括，二者应保持一致。

**第六章固定栏目为交付完整性要求**：（二）（三）（四）为每份主流程交底书的固定栏目，不得省略；某栏目内容确无时写明「无／由代理人补充」，并列入交付检查记录待补项。

**背景收敛门禁（一、二章）**：背景与技术问题须收敛成**一条主线**——梳理现有技术缺陷后归纳为**一个核心总技术问题**，全文最终指向**一个主技术效果**，不要罗列一堆分散的子问题和分散效果。次要缺陷/子效果如确需保留，作为主问题/主效果的下位展开或从属保护点，不与主线并列争焦；第二章「所要解决的技术问题」以该总问题为纲，与第四章有益效果的主效果、第五章保护点首尾呼应。

**实施例收敛门禁（六、（一））**：一个完整、可复现的实施例即可——写清**输入 → 可复现的计算/处理过程 → 最终输出 → 可验证结论**，参数给具体基准值并注明「不作为权利要求限制」。不要堆多个平行实施例充数；确有本质不同的替代实现，归入（二）可替代实施方式简述，不再另铺完整实施例。

**核心口径单一真源门禁**：核心术语、符号、删/留项、实施例基准数值**一次定死**，并在**说明书正文、权利要求书、附图（含附图说明）**三者间保持一致——改一处须联动其余，不留并行两套叫法或两套数值。全文同一概念用同一术语与符号（自造词首现即定义），基准数值在实施例、（六）参数表与效果论述中一致；发现三稿口径不一致按 `disclosure_self_check.md` §8.1 回改。

**无关内容不硬塞门禁**：与本案核心方法无关的内容不得为凑篇幅硬塞进正文。对基于项目本地文件的现成成果（既有报告、图表、代码注释、他案片段等），写入正文前须再三判断其是否真正服务于本案区别特征与技术效果，并**先与用户确认**再采用，不默认搬运（与定位锚「与核心方法无关不内置」一致）。

**章节编号硬性门禁**：主流程交底书正文使用「一、二、三」和「（一）（二）（三）」组织章节；流程步骤使用 `S1、S2、...`；附图使用「图1、图2、...」。不得生成 `## 1. 技术领域`、`### 2.1 已公开技术概况`、`### 3.4.1 ...` 这类 Markdown 标题编号。编号型列表只用于局部条目，不得作为跨章节标题体系；转换为 Word 时不得进入 Word 自动编号系统，须以字面局部编号显示，避免跨章节续号。

> **编号指代约定（内部）**：本技能各 prompt 与自检中出现的 **`3.4.1 符号表`** 指的是正文 **三、（五）符号与公式**；**`3.5 参数表`** 指的是正文 **三、（六）关键技术参数**。这些是**内部指代简写，不是正文标题**——正文一律用中文编号（三、（五）/（六）），**不得**把 `3.4.1`/`3.5` 渲染成正文标题。自检按内容（符号表/参数表是否存在、是否同形）核对，不依赖字面 `3.4.1` 标题。

**案件名称默认规则**：若上游存在候选主题卡（T0 产出），Step 7 案件名称**默认采用主题卡的「简洁题名」（≤25 字）**，不得擅自改用「完整技术路线名」。完整技术路线名可用于三、（一）方案背景或交接说明，不作为默认案件名称与专利名称。

**发明名称不堆客体（全入口通用）**：无论是否经 T0，发明名称以方法主线为准（可含「及系统」），**不得**在题名中罗列「设备」「存储介质」「程序产品」等客体（「…方法、系统、设备及存储介质」为典型模板化痕迹，须收敛为「…方法及系统」）；客体组合只在第五章保护点布局中体现。≤25 字规则对非 T0 案件同样适用。

**mermaid 图 A4 排版要求**：系统框图（三、（二））与流程图（三、（四））转 PNG 后须能在 **A4 一页内清晰放下**。生成 mermaid 时：①节点多于约 8 个时优先用纵向布局（`flowchart TB`），避免横向 `LR` 过宽；②节点标签精简（关键词而非整句），必要时用 `subgraph` 分层收拢；③单张图控制在约 12 个节点内，超出则拆成"总框图 + 分模块图"多张；④避免超长边标签。定稿视觉 QA 时若发现图溢出页面或线框重叠，须回改 mermaid 再渲染。

### 附录 A：结构类有限辅助章节结构

> 本附录仅在 `intake.md` Q1.5 B 路线生效时使用。本技能对结构类方案不做专利点挖掘和创造性评估，附图须用户自备，物理机理须由用户提供实验、仿真、标准或工程数据依据；自检结果最高为 WARN。

```
1. 注意事项
2. 一、介绍相关技术背景，描述与本发明技术最相近的现有技术，并说明该现有技术存在的缺点
   - 1.1 现有技术（按技术方向分类，含专利检索结果）
   - 1.2 现有技术存在的缺点
3. 二、针对上述缺点，说明本发明所要解决的技术问题
4. 三、本发明技术方案的详细阐述
   - 3.1 技术方案概述（发明核心思路，1-2段概括）
   - 3.2 结构附图及部件编号说明（附图清单 + 统一编号表，不用 mermaid）
   - 3.3 各部件结构与功能说明（逐部件说明形状、材料、连接关系、位置关系，聚焦结构特征而非功能性描述）
   - 3.4 工作状态/动作过程说明（按状态或工位逐段描述：正常→失效→保护→终态，结合附图标记）
   - 3.5 关键结构参数与设计约束（尺寸关系、公差、材料性能约束等，有公式时遵循 §7.7）
5. 四、与现有技术相比，本发明具有哪些优点？
6. 五、本发明的技术关键点和欲保护点是什么？
7. 六、其它（具体实施方式、技术效果、参数示例）
```

**结构有限辅助 §3.2 撰写要求**：

1. **附图清单**：列出全部附图编号与标题（如「图1 正常插合状态剖面图」「图2 微分离等势旁路状态剖面图」），说明各图视角（剖视、俯视、局部放大等）
2. **统一编号表**：全部件用阿拉伯数字编号，格式为「编号-名称」（如「1-公头壳体、2-母头壳体、3-插针导体」），编号须全文统一、附图与文字互斥（同一标记不在同一附图上同时标文字说明）
3. **附图本身**不由交底书 Markdown 生成，由用户提供 CAD/Visio 线稿或手绘草图；交底书中以文字描述附图内容

**结构有限辅助 §3.3 撰写要求**：

- 逐部件说明时，使用**结构特征**（形状、构造、连接关系、位置关系、材料）而非功能性限定
- 正确示例：「同极等势旁路接触件 6 为弧形弹性导电片，一端固定于插针导体 3 的根部，自由端沿轴向延伸并超出主接触区 5 的末端」
- 错误示例：「旁路件用于在主接触失效时提供等电位保护」（这是功能描述，不是结构特征）
- 每个部件说明中应明确其与相邻部件的**位置关系**和**连接方式**

**结构有限辅助 §3.4 撰写要求**：

- 按**状态/工位**分段描述，每段对应一张或多张附图
- 描述顺序应体现部件之间的**动作顺序**和**位移关系**
- 每段须引用具体附图编号和部件编号（如「参见图2，当主接触对（插针导体 3 与插筒导体 4 构成的主弹性接触区 5）发生微分离时……」）
- **技术闭环必须完整**：从正常状态到最终状态（保护/失效/维护），每个阶段都要有对应描述和附图支撑，不得在中间状态断裂
- **主实施例须收敛**：每个部件在主方案中只选定一种具体形态（如旁路件选定「弧形弹性导电片」），其余变型放入第六章实施例或从属权利要求

**结构有限辅助 §3.5 撰写要求**：

- 结构参数表：列出关键尺寸、间距、行程、公差等设计约束
- 参数须有明确的物理含义和来源依据（实验、仿真、标准规范）
- 无可靠来源的具体数值不要写入，改用设计约束关系（如「旁路接触行程 > 主接触行程 + 安全裕度」）
- 有公式时仍遵循 §7.7 符号与公式体例

**现有技术部分撰写硬性要求**：每一条现有技术（专利或文献）**必须在证据包中**具有经核验公开源 URL 或明确的未核验状态；**正式交底书正文原则上只写公开文献标识（公开号/标题）、技术方向、接近点与区别结论，不强制放 URL**（若放，须为已核验稳定源；`third_party_not_indexed` 等未核验链接一律不入正文，与 `prior_art_search.md` 正文规则、`formal_disclosure_cleanliness.md` 一致）。**国知局检索**（`EPUB_HITS_JSON`）中对该专利给出的 **`abstract` 非空时**：文中「技术方案 / 应用 / 局限」类表述**须以摘要理解为前提**（消化后重写，非整段粘贴），**禁止**与摘要明显矛盾或脱离摘要杜撰；详见 **`prior_art_search.md`**「`abstract` 必用」。

**授权论证闭环（全文硬性要求）**：交底书必须能读出以下链条：

```text
现有技术缺点 -> 要解决的技术问题 -> 区别技术特征 -> 作用机理 -> 技术效果 -> 欲保护点
```

- 第一章写“现有技术缺点”时，优先围绕 Step 5 查新中最接近现有技术的不足，不要泛泛写行业痛点。
- 第二章的技术问题须从第一章缺点自然推出，避免写成商业目标或产品愿景。
- 第三章须把可用区别特征写成可实施的步骤、模块、结构、连接关系、参数关系或处理逻辑。
- **核心动作可实施性门禁（生成时执行）**：第三章凡出现「识别、判断、映射、匹配、选择、优化、调度、预测、评估、归因、修正、校验、排序、分配」等核心处理动作，须补足：①输入数据或前置条件；②处理依据（规则/模型/阈值/映射关系/约束/流程）；③输出结果及其进入的后续步骤；④数据缺失、冲突、多候选或低置信度时的处理方式。四项缺失则该动作写成了抽象功能，须补实施规则。
- 第四章的技术效果须由第三章技术特征产生；没有来源或机理支撑的效果，写为“预期可改善/待测试验证”，不得写成已验证事实。
- 第五章保护点须回扣第三章的区别技术特征，不把无实施支撑的愿望、场景或结果写成核心保护点。
- **独权联动闭环（A 路线）**：第五章独立保护点主线须写成步骤间**显式参数耦合/因果依赖**的联动链（步骤 N 的输出约束步骤 N+1 的行为），不得写成可拆分的并列指标组合（「计算指标 A、计算指标 B、按规则选择」式）；并列式独权易被认定为常规评价手段的简单叠加，命中时按 `patent_points_analyzer.md`「独权联动闭环检查」改写或重构保护点。

**方案骨架先行与步骤分级公开（生成顺序门禁，两案代理复盘）**：真实案件复盘显示，系统框图、模块说明、方法流程、保护点**各自独立生成**必然漂移（代理批注「3.2 与 3.4 流程逻辑不同，以哪个为准」）。规则：

1. **骨架先行**：写正文前先固化一份**统一步骤骨架**（内部产物，落案件目录 `方案骨架.md`，不入正文），每步至少含：步骤 ID、名称、输入（来源）、操作与依据、输出（去向）、异常分支、对应公式编号、步骤类别。三、（二）系统框图、（三）模块说明、（四）流程说明与第五章方法保护点**均从同一骨架展开**；各视图允许粒度不同，但须能一一对应或一对多映射（映射关系写入骨架），**不得**让各章节自由发挥出骨架之外的步骤或分支。修改任一视图的步骤划分时，先改骨架、再联动改其余视图。
   **骨架升级为技术证据合同（测量/诊断/定位/状态识别/多模态证据类案件必做）**：凡输出包含「定位/识别/归因/判定某物理对象状态」且输入为传感/量测数据的案件，骨架须按 **`templates/technical_evidence_contract.yaml`** 升级为完整**技术证据合同**——在骨架字段之上增加观测层级与可声称精度（rank）、基线登记（standard/historical_clean/post_treatment/healthy_peer 四类，标准参考不得写成现场观测）、阈值来源、下游消费者、降级分支和特征分类（independent_core/dependent/**implementation_param**/auxiliary_evidence；采样周期、示例阈值、设备配置属实施参数，独权上位化为「预设周期/预设阈值」）。多模态证据并用时同步填 **`templates/evidence_responsibility_matrix.md`**。规则详见 **`references/technical_evidence_contract.md`** 与 **`references/observability_and_multimodal_evidence.md`**；合同未固化不进入正文生成，机器校验由 `delivery_gate.py` C12 兜底。
2. **步骤分级公开**（直接对应代理要求「独特操作详述、常规操作简述」）：骨架中每步标注类别——`CORE`（构成区别特征的核心步骤）／`SUPPORTING`（支撑核心的必要步骤）／`COMMON`（本领域常规步骤）／`OPTIONAL`（可选/可替代）。`COMMON` 只须简要说明常用实现方式（一两句，如「候选配置可由规则枚举、外部优化器或用户指定生成」）；`CORE` 与关键 `SUPPORTING` 须完整展开：除上文「核心动作可实施性门禁」四项外，涉及**校核/判定**的还须写明**全部约束条件清单、同时满足哪些才算通过、不通过时的处理**（反例：只写「S4，校核台账」）。避免两个极端——常规输入写很长、核心计算一笔带过，或所有步骤平均用力。

**公式随步走（公式-步骤绑定门禁）**：公式集中罗列而不绑定步骤会被代理人整节退回（「该部分公式具体对应方法中的哪一步骤，建议插入对应步骤」）。规则：

- formula manifest 每条关键公式须填 **`owner_step`**（归属的骨架步骤 ID）；无归属步骤的公式不得进入正文（要么补步骤、要么删）。
- 每条公式须在其 owner_step 的 3.4 流程叙述中**出现或被显式引用**（如「按式 (6) 解析得到 \(p_{\min}\)」），并交代该式的输入来源、适用前提与输出去向；（五）符号与公式节只承担**符号定义与公式索引**职责，不得成为公式的唯一出现位置。
- **变量血缘**：公式中每个变量须为外部输入、前序步骤/台账输出或已定义派生量之一，禁止公式中突然出现未定义或来源不明的参数（与 §7.7 符号表先行联动）。

**术语定义与数据血缘门禁**：

- **自造词首现即定义**：非本领域通用术语（如「清洁基线数据」「边界函数系数」「风险代理」类自造/半自造词）在首次出现处即给出：含义、获取或计算方式、单位或取值范围；第六章术语表为全文唯一口径。不得让代理人来问「该词语非专有名词，请解释其含义」。
- **集合术语不与成员并列重复**：定义了集合术语（如「边界函数系数，包括 X 序列、Y 序列…」）后，后文引用**只用集合名**，不得写「基于所述边界函数系数、X 序列、Y 序列…」式的重复并列（被追问「是否存在重复」）；若成员边界不清，宁可不设集合术语、直接列举。
- **数据血缘分层**：原始采集量 → 预处理/归一化量 → 派生特征 → 中间判断结果 → 决策输出，五层身份不得混写；「特征清单」不得与「原始数据清单」互相混入（反例：把派生的组串功率残差列进 S1 原始采集数据）；每个派生量须能答出「由哪一步的哪些量按什么规则算出」。「提取／计算／生成／解析」等动词按实际数据层级使用，不混用。

**模糊限定词与观测粒度门禁**：

- **模糊限定词量化三选一**：「近似同步、明显大于/小于、基本一致、较高/较低、风险较低、证据不足、必要时、视情况、适当」等出现在**判定语境**时，须给出①数值阈值/范围、②相对比较基准、或③组合判定条件之一（如「近似同步下降」→「损失率差值不超过预设同步阈值（示例 3 个百分点）」；「证据不足」→「最高候选得分低于阈值，或前两名得分差低于区分阈值，或多源证据冲突」）。无实际标定依据时**给示例值并注明「示例阈值，需按实际数据/工程样本标定」**或标「待发明人确认」，**禁止**虚构已标定数值（与「诚信与支撑边界」联动；`tools/delivery_gate.py` C11 机器兜底 WARN 列出待判定处）。
- **观测粒度匹配**：凡「定位、映射、识别、反推、确定具体区域」类主张，先核对**输入数据粒度是否支撑输出粒度**（反例：仅组件/组串级整体 I-V 曲线不支撑唯一定位到具体电池片）。不支撑时降级措辞——「确定」→「确定候选」、「定位到」→「映射至可能受影响的」，输出候选区域＋置信度，并写明消歧所需辅助数据（分段采样、图像、红外等）；具备辅助数据时才可写进一步细化定位。
- **多依据判定连词一致 → 决策表单一事实源**：「基于 A **和** B」与「基于 A **或** B」含义不同；同一判定依据在模块说明、流程步骤、图注与保护点中的连词须全文统一（反例：S8 写「形态和机理」、图 5 说明写「根据机理」）。**多条件判定须先建决策条件表**（技术证据合同 `decisions` 段或 **`templates/decision_table.md`**）——AND/OR 只在表中显式写出并赋 D 编号，正文各视图一律引用编号而非另写条件；降级/兜底分支（证据不足、冲突、低置信度）同样入表编号，不散落为「必要时……」（`delivery_gate.py` C13 核对编号引用一致性）。

**软件/AI 案件特别要求**：算法、模型、商业规则或数据处理特征不能孤立写成抽象规则；须说明其与具体技术场景、硬件/系统模块、输入输出、训练或推理流程的配合关系，以及由此解决的技术问题和产生的技术效果。涉及 AI 模型时，按需要披露模型模块、层/连接关系、训练步骤、关键参数、输入输出和应用领域组合，使本领域技术人员能够实施。

**默认保护组合**：主流程优先按「方法 + 系统/装置 + 电子设备 + 计算机可读存储介质 + 计算机程序产品」**五客体**组织第五章保护点（计算机程序产品为 2023 版《专利审查指南》明确的权利要求主题，适合以在线分发/云端部署实施的方案）。若查新结果或材料支撑不足，可收缩为「方法 + 系统」或「系统」；若方法/控制创新与结构改进并存，优先把方法/控制作为主线，结构侧写入从属特征、实施例或另案建议。设备/介质/程序产品为覆盖面客体（尾部保护），不作为区别现有技术的主线，不进入发明名称。

**诚信与支撑边界**：不得编造实验数据、性能提升比例、技术效果、参数来源或用户未提供的事实。确需表达但资料不足时，标注为“待补充实验/仿真/样机验证”或改为定性技术效果。

**技术效果的正文措辞门禁（正式正文，重要）**：诚实性体现在**不编造、不夸大**，而非在正式申请文本中作竞争性自陈。仿真/实测显示本方案在某些场景**不优于或劣于现有路线**时——
- **正式交底书/说明书正文不得**写“本方案尚未优于/劣于现有路线”“工程化待优化”“某场景表现更差”等**竞争性不利陈述**（易在审查或无效程序中被作为不利证据）；
- 应将该情形**如实但正向地重构为方案自身的鲁棒性/安全能力**，例如“在预测误差较大或可调资源不足时，通过残余风险校验与告警显式输出不可完全消除的风险，实现可解释性与安全降级”——描述的是同一事实（未必消除越限），但落点在本方案的技术特征而非与他方的优劣比较；
- **完整的、含不利项的对比数据留在内部**（`claude/GPT 复核记录`、查新证据包、交接说明），不进入正式正文；
- 正文只保留**本方案成立的正向定量效果**（须真实、可复现）+ 必要的验证阶段标注（“具体数值以进一步仿真与现场验证为准”），**不写**“单次仿真/尚未优于”等自我贬损。

**防御性判断与正向表述门禁（正式正文，重要）**：防御性/否定式判断（防止独权写偏、客体主线取舍等**代理人策略提示**）属**交接说明、审稿意见、查新记录**范畴，**不进入正式正文的主叙事**；正文一律用**正向技术特征与技术效果**表达。同一判断换正向写法即可两全——既守住了撰写取向，又不主动压窄保护面：

1. **兼容而非排除**：不写“本发明不在于/不采用 X”，写“本发明可兼容 X（如幂律、对数律、稳定度修正、回归或机器学习模型）；区别在于[正向机制]”。否定式会主动放弃 X 相关的保护面。
2. **效果正向列举而非自我弱化**：不写“不以平均误差显著降低作为唯一评价目标”，写“除风速/功率/AEP 加权误差改善外，还提供策略来源、回退层级、验证误差与风险提示信息”。转向可追溯性/稳健性须用**加法式**（“除…外，还…”），不用**免责式**（“不以…为目标”），后者在正文读作效果不强（与「技术效果的正文措辞门禁」及 `disclosure_self_check.md` §8.5 幅度-措辞门禁联动）。
3. **产品承诺→上位技术输出**：不写“不强制输出未标注风险的外推值”这类产品行为承诺，写“生成风险提示信息，所述风险提示信息包括低可信标识、不可行原因、复核提示、补测建议或候选策略不可用原因中的至少一种”。
4. **代理人策略提示不入正文**：如“电子设备/存储介质不宜作为区别现有技术主线”“本案可发表价值在于…”“建议独权收窄为…”是审稿/交接提醒；正文只写“本发明还可通过电子设备、计算机可读存储介质或计算机程序产品实现”。
5. **独权收敛但说明书不自我否定**：独权可收敛为核心闭环（如三段联动），但说明书正文应表现为“上述模型与数据源均可纳入该闭环”，**不写**“这些都不是本发明”式自我否定。
6. **独权抽象、实施例具体**：具体形态（如六类分箱策略）写实施例或从属权利要求；独权写“至少包括基础策略与回退策略”“至少两类候选策略”等上位限定，避免被单一实施例绑死。

Step 8 以一道**否定式表述扫描**兜底（见 `disclosure_self_check.md` §8.3；`tools/delivery_gate.py` C10 机器列出 `不在于/不作为/不强制/不以/不宜/显著降低` 供逐处判定归属）。这些词非绝对禁止，但每次出现都须判定：属代理人提示→移交接说明；属技术特征→改正向限定。

**控制/调度类方案公式支撑门禁**：涉及状态量递推（如储能 SOC、温度、队列）或约束（如订单承诺、安全边界）的控制方法，第三章须给出：①被控量/状态量的**递推或合成公式**（含效率、容量、步长等）；②约束的**定量表达式**（如“订单最低必需功率 = 剩余电量 / 剩余时间”），使订单/服务类约束呈现为**技术约束而非管理规则**，降低客体风险并满足可实施性；③**约束不可满足时的处理**——须说明约束无法满足（如订单已到期、最低必需功率超过最大能力、资源耗尽）时的降级方式（不可满足标记 + 告警/安全降级），**不得**写成“保证/一定不违约/必然满足”等无边界的过强承诺（否则支撑过强、易被举反例）。④对时序量（如未来时域越限量），残余/校验类计算须**逐预测步重估后取极值**，不宜只用单点标量近似。

**仿真/实测结果的正文限定**：正文引用仿真或实测的**绝对量化表述**（如“100%”“全部场景”“均为…”）须限定到“**在所述（工程仿真/实验）实施例中**”，不作为普遍结论；配合上「技术效果正文措辞门禁」的验证阶段标注。

**禁止输出**：交底书正文中**不得**包含「自检清单」章节，例如检查项表格或带状态符号的清单列。自检见 `disclosure_self_check.md`，**内部执行**，不写入交付正文。

**禁止仓库/技能脚注**：交付用 Markdown **末尾不得**出现任何指向本技能或示例仓库的说明，例如「本文件为 `patent-unveil-review` / `patent-disclosure-skill` 仓库内教学示例」「不构成任何法律或技术承诺」「虚构教学」「详见 `examples/`」等。正文**止于第六章及此前章节**；**不要**在文末追加斜体免责或仓库署名。

**正式正文清洁门禁**：交底书正文不得出现 Agent/Codex/Claude/WebSearch/Playwright、脚本名、提示词、自检、DOCX QA、Word/LaTeX 中间稿、案件证据包、检索式、截图编号、商业库会话 URL、来源状态标签或“详细检索记录已另存”等流程说明。确需提示用户或代理人的内容，写入 `交底书交接说明_*.md`、`交底书交付检查记录.md` 或查新证据包，**不写入** `.md` / `.docx` 正文。详见 `references/formal_disclosure_cleanliness.md`。

## 7.3 输出文件命名（用户产出目录，必遵循）

在用户目录（如 `outputs/{案件标识}/`）写入交底书 **Markdown / Word** 时，**主文件名须体现正文中的「案件名称」**，且**凡向用户落盘交付的定稿均须带时间戳后缀**（见下第 5 点），避免无区分度的固定名（如一律 `disclosure_draft.md`）。**仓库内 `examples/` 为教学统一可仍用固定名**；用户产出不适用该惯例。

1. **提取**：从 `**案件名称**：` 行取完整发明名称；去掉占位（如 `[待填写]`、`【待填写】`）、首尾空格。
2. **规范化**：删除或替换 Windows 非法字符 `\ / : * ? " < > |` 与换行；连续空格可压为单个空格或删去（中文标题通常无空格亦可）。
3. **长度**：文件名（不含扩展名）建议 **≤ 80 个字符**；超长则**截断**到约 80 字并保留语义完整（例如截在「方法及系统」等结尾词之前），勿用无意义随机串。
4. **定稿命令**：`mermaid_render.py` 的 `-o` / `--docx` 须使用**同一主文件名**，且该主名**必须符合第 5 点**（**案件名 + `_` + 14 位时间戳**，多来源并行时再加可选 `_{producer}`）。示例（案件名已按上文规范化、过长已截断时）：

   `python3 tools/mermaid_render.py -i "…草稿.md" -o "一种异构计算环境下基于资源画像与限频重排队的批任务调度方法及系统_20260408143025.md"`

   默认同目录生成同名 `.docx`。过程性中间稿（仅自用、非交付）文件名可自定，但**最终交付**不得省略时间戳。

5. **时间戳后缀（凡落盘交付必遵循）**：凡写入用户产出目录、作为**向用户交付**的技术交底书 **`.md` / `.docx`**，主文件名须为：  
   **`{§7.3 规范化案件名}_{YYYYMMDDHHmmss}.md`** 与同名 **`.docx`**。  
   - **首次定稿**与**迭代合并/纠正**适用**同一规则**；每次交付取**当次落盘时**的**本地时间** 14 位数字（年月日时分秒各 2 位，如 `20260408143025`）。  
   - **不要覆盖**已有交付文件；新一次交付即**新时间戳**、新文件名。用户**明确要求**覆盖某路径时从其意。  
   - **多来源并行（可选）**：多个 Agent/产线同时产出时，在时间戳后加 **`_{producer}`**，即 **`{规范化案件名}_{YYYYMMDDHHmmss}_{producer}`**；`producer` 仅用英文字母、数字或连字符（如 `codex`、`claude`）。各版本并存，由用户选用，不强制合并为唯一终稿（SKILL.md G2）。`delivery_gate.py` C6 两种形式均接受。
   - **`mermaid_render.py`** 的 `-o` 与可选 `--docx` 须与上述主名一致。  
   - **例外**：（1）仓库内 **`examples/`** 示例可继续固定文件名；（2）用户书面指定文件名时从其意（仍建议保留时间戳以免混淆）。

Agent **落盘时**即采用上述命名，并在回复中写明路径，便于用户对照标题与磁盘文件。

## 7.4 图示要点

### 主流程系统框图与流程图

- **系统框图与流程图**均仅用 **fenced mermaid**（本地 `mmdc` 渲染，不依赖外网 PlantUML）；定稿 Markdown 中必须由 `mermaid_render.py` 追加**可见** `![图示 n](...)` 图片引用，Word 中以 PNG 为准，**无需**再附 ASCII 文字框图
- mermaid 内节点标签用简短中文/数字，避免 ①②③。可另写简短「流程说明」段落概括各步，**不得**用 ASCII 框线箭头代替图示
- **可编辑矢量图（按交付对象需要）**：若交付对象（代理人/制图）需要**再编辑**图示，除 PNG 外应同时提供**文字可选中的可编辑矢量图**——用 mermaid-cli 导出 SVG（`mmdc -i 图.mmd -o 图.svg`），或把框图/流程图整理为**可编辑 PPT**（用形状与文本框，而非整页位图）；不要只给不可编辑的位图。正式定稿 Word 仍以 PNG 呈现，可编辑矢量件随交接说明附带

### 结构有限辅助附图

- **正式附图**须为黑白线稿（CAD/Visio/手绘扫描），由用户或制图人员提供，交底书中以文字描述附图内容
- 交底书 Markdown 中**不强制**使用 mermaid，但可**选用** mermaid 画以下辅助图：
  - 状态转移图（`stateDiagram-v2`）：展示连接器从正常→失效→保护各状态的转移关系
  - 动作时序/位移顺序图：展示各部件的动作先后关系
- 辅助 mermaid 图**不替代**正式结构附图，仅用于帮助代理人理解工作原理
- **CNIPA 附图硬性要求**（详见 `references/structural_patent_requirements.md`）：
  - 黑色墨水线条，不得着色、不得使用照片、不得有灰度阴影或渐变填充
  - 部件编号用阿拉伯数字，用引出线指向对应部件
  - 同一部件在不同附图中编号必须一致
  - 附图标记与说明书文字互斥（同一标记不在附图上同时标文字说明）

## 附录 A.1 结构有限辅助语言规范与权利要求指导

> 仅在 `intake.md` Q1.5 B 路线生效时使用。以下内容只用于文字清洁、附图标记一致性和结构权利要求格式参考，不构成创造性评价。

### 语言清洁要求

结构类交底书容易出现以下**必须清除的**语言问题：

| 问题类型 | 示例 | 改法 |
|---------|------|------|
| 报告式/分析式语言 | 「本交底书围绕……进行检索」「经综合对比分析」 | 删除，专利交底书不是分析报告 |
| AI生成残留 | 「实际申请时可由制图人员……」「不以某一在先申请……作为必要条件」 | 删除，交底书是技术公开文件，不是工作备忘 |
| 不确定/对冲表述 | 「可以是A，也可以是B，还可以是C、D、E」（在主方案中并列过多替代件） | 主方案固定一种，替代形态移入实施例或从属权利要求 |
| 功能性限定滥用 | 「用于实现等电位保护的旁路件」 | 改为结构特征：「弧形弹性导电片，一端固定于插针导体根部，自由端沿轴向延伸」 |
| 参数来源不明 | 「间距为0.216 mm」（无数据来源） | 删除具体数值或补充来源依据，改用设计约束关系 |

### 权利要求撰写指导

**结构类独立权利要求**应优先采用"两段式"写法（前序部分 + 特征部分）：

```
一种[产品名称]，包括[已知结构部件]，其特征在于：
还包括/所述[部件名称]为/设有……[用结构特征限定创新点]
```

**结构特征限定顺序**：形状 → 构造 → 连接关系 → 位置关系 → 材料 → 尺寸比例关系

**避免在独权中**：
- 使用纯功能性限定（如「用于……的部件」）
- 包含方法步骤（结构独权中不写操作动作）
- 引入非必要技术特征（缩窄保护范围）
- 强制要求可选功能（如「旁路断开」若非核心创新则不应放独权）

**从属权利要求金字塔**：从独权出发，逐层增加具体结构细节、材料选择、参数范围、替代形态、附加功能等。

## 7.7 符号与公式体例（必遵）

撰写 **3.4.1**、**3.5** 及全文含 LaTeX 的段落时须遵循；正/反例与符号表示例见 **`template_reference.md` §3.4.1**。

### 公式 manifest 先行

- 出现 3 条以上关键公式、价格/能量/控制边界公式、或用户指出公式错误风险时，须先建立 `formula_manifest`（可从 **`templates/patent_formula_manifest.yaml`** 复制），每条至少含：`id`、`number`、`title`、`latex`、`display`、`dimension_check`、**`owner_step`**（归属的方案骨架步骤 ID，见「公式随步走」门禁；无归属步骤的公式不得进正文）。
- 关键公式的 `latex` 字段是唯一公式源；正文 3.4.1 只引用或复制 manifest 中的公式，不得由 Agent 在正文临场重新拼写。
- 公式编号由 manifest 的 `number` 管理；正文不得靠大量空格手动右对齐编号。Word 中带 `\tag{}` 的块级公式由 `md_to_docx.py` 写为无边框两列表格：左列公式居中，右列编号右对齐。
- 每条关键公式必须有量纲或取值校核；例如储能能量状态 \(B_{s,t}\) 的单位为 kWh，不得写成无量纲 SOC。若需要 SOC，应另定义 \(SOC_{s,t}=B_{s,t}/B_s^{\max}\)。

### 符号表先行

- 撰写 **3.4.1** 或全文含 LaTeX 时，**先写符号与变量定义**（可按（1）任务/对象下标、（2）节点/环境下标、（3）标量与向量分组），每项至少含：**符号、含义、下标含义（如 \(i\)=任务、\(j\)=节点）、量纲或取值范围**。
- 其后公式、**3.5 参数表**、**第六章实施例**中出现的符号须与符号表 **同形、同义**。
- **禁止同一字母多义**：例如任务侧权重用 \(b\)，节点侧饱和度应改用 \(g\)、\(h\) 等其它字母，勿任务/节点共用 \(b\) 表示不同物理量。

### 下标与上标

- **资源维度/类型标签**（cpu、mem、io、peak 等）一律写入 **下标**，维度名用 `\mathrm{cpu}`、`\mathrm{mem}` 等正体，例如 `b_{i,\mathrm{cpu}}`、`a_{j,\mathrm{mem}}`。
- **禁止**用 `^{cpu}`、`^{mem}`、`^{io}` 等 **上标** 表示维度或字段名（易被读作幂次，亦不符合专利正文常见写法）。
- **上标仅用于**：幂次、转置、序号、撇号类标记；**下标用于**对象编号与维度标签。

### LaTeX 分隔与写法（全文统一）

- **行内公式**：全文统一 **`\(...\)`** 或 **`$...$`** 二选一，**不得混用**。
- **块级公式**：全文统一 **`\[...\]`** 或 **`$$...$$`** 二选一，**不得混用**。
- **禁止代码样式公式**：正文、表格和符号列中的符号/公式不得用反引号包裹，尤其不要写成 `` `B_{s,t}^{tot}` `` 这类代码样式；应写为 \(B_{s,t}^{tot}\) 或对应的统一分隔符形式。
- **Word 交付**：`.docx` 中的符号与公式必须是 Word 原生可编辑公式（OMML），不得把公式截图、公式 PNG 或代码样式文本作为正式公式交付。Mermaid 图示可以是 PNG，公式不可以。
- **DOCX QA**：Word 生成后必须运行 **`tools/qa_docx_math.py`**；含 manifest 时使用 `--manifest <manifest.yaml>`，正式正文须使用 `--check-formal-text`。该工具是 Word XML 级交付门禁，不只检查公式，还检查未渲染 mermaid 源码（如 `flowchart TB`）、Consolas/代码样式残留、Word 自动编号结构、嵌入媒体数量不足和流程说明残留。若发现 `frac{`、`mathrm{`、`\(`、`\)`、`$` 等残留，或 manifest 编号/分式/上下标结构校验失败，或图示源码/自动编号结构/内部流程说明进入 DOCX，本轮不得作为定稿交付。
- 比较符优先写 `\leq`、`\geq`（定稿工具可兼容 `\le`/`\ge`，正文仍推荐 `\leq`/`\geq`）。
- 块级公式尽量 **单行写完**；需编号时优先使用 manifest `number` 并在块级公式末尾写 `\tag{1}`，由工具结构化排版编号；不要使用空格对齐。
- 逻辑连接词（「且」「或」）优先写在公式 **外** 的中文叙述中；若必须写入公式内，用 `\land`/`\lor`，**避免** `\text{且}` 等复杂文本命令（定稿渲染易失败）。
