# 迭代模式：代理意见闭环

来源冻结 → 原文包 → 作用范围 → 分诊 → 修订 → 逐条回复 → 经验回写。

## 局部执行契约

- **Purpose**：把不同载体中的代理意见转为可追溯、可验证的修订任务，并形成与实际修改一致的处置矩阵和职业化回复。
- **Inputs**：代理意见来源（批注 DOCX、逐字文字、消息导出、用户转述或 OCR）、正文基线稿、案件目录；已有可信 overlay 时可从 R4 开始。
- **Outputs**：规范 JSON 原文包、可读提取稿、定位 overlay、新时间戳修订稿、`批注处置矩阵.md`、需要时的代理意见回复稿、留档摘要和经验回写。
- **Must**：冻结并标记来源；逐字保留可获得的意见；区分原文、转述和 OCR；对已落实/部分落实项登记机器锚点；使回复条数等于经确认的顶层意见条数。
- **Must not**：因为没有批注 DOCX 就停工或虚构 DOCX 锚点；改写、合并原文；把转述/OCR 冒充原始批注；把内部判断直接当对外状态；声称已修改但稿内无对应变化。
- **Completion criteria**：每条顶层意见均有完整矩阵行、对外四态、`CLOSED/PARTIAL/OPEN` 状态和必要锚点；多子要求逐项核对；修订稿与回复一致；机器门禁、人工语义复核和经验回写完成。

先完整读取 `prompts/iteration_context.md`。完成 R1–R3 后，分诊和改稿按 `prompts/correction_handler.md` 执行。意见原文在全流程中不可变。

## 何时启用

- 用户给出批注 DOCX、逐字粘贴文字、邮件/消息导出、转述或 OCR 文本，并要求提取、定位、落实或逐条回复。
- 用户已提供带 `REVIEW_COMMENT_BEGIN/END` 标记且来源可信的 overlay 时，可跳过 R1–R3。
- 用户只说“代理有意见”但未提供具体内容时，先继续盘点已有案件文件；仍找不到意见源，再请求用户提供文字或文件。不要擅自猜意见。

## R1 冻结来源并生成规范原文包

先确定 `{producer}`（如 `codex`、`claude`、`human`）和 14 位时间戳。原始输入只读保留，不就地改写。规范 JSON 是后续 C14 与 Markdown 展示的共同真源。

### A. 带批注 DOCX

```text
python <SKILL_ROOT>/tools/docx_comment_extract.py --input "{审阅版.docx}" --json-output "{案件目录}/代理意见原文包_{YYYYMMDDHHmmss}_{producer}.json" --output "{案件目录}/代理意见原文包_{YYYYMMDDHHmmss}_{producer}.md" --producer "{producer}"
```

工具保留顶层批注与回复线程、原生 ID、作者、日期、范围/点批注、锚定文字、段落上下文和已解决标记。`range_exact` 只代表工具定位到 Word 范围，不代表该范围就是代理人实际意图的全部作用范围。

### B. 文字、消息导出、转述或 OCR

把用户实际给出的文字原样保存为 `代理意见输入_{YYYYMMDDHHmmss}_{producer}.txt`，再按真实来源导入：

```text
python <SKILL_ROOT>/tools/attorney_comment_import.py --input "{代理意见输入.txt}" --source-type "{pasted_text|text_file|message_export|user_paraphrase|ocr_source|structured_table}" --output-json "{案件目录}/代理意见原文包_{YYYYMMDDHHmmss}_{producer}.json" --output-md "{案件目录}/代理意见原文包_{YYYYMMDDHHmmss}_{producer}.md" --producer "{producer}"
```

规则：

- 只有明确编号或列表标记才自动拆为多条。
- 无编号文字默认是一条暂定顶层意见。只有用户明确同意时才用 `--split-paragraphs` 暂按段落拆分。
- `user_paraphrase`、`ocr_source` 和 `count.status=provisional` 必须在回复中提示待确认，不得称“已完整提取原始批注”。
- 工具无法解析 DOCX 时，记录失败并请求 Word 导出或逐字转录；不得静默降级为无来源清单。

落盘 JSON 为机器真源；末行 `COMMENT_EXTRACT_JSON` 仅供流水线读取。回复轮 DOCX 只把顶层代理意见计入 C14，已有回复作为上轮记录。

## R2 恢复作用范围

每条意见补充：

| 字段 | 规则 |
|---|---|
| 锚定对象 | 范围批注＝锚定文字所在章节/条目；点批注＝所在段落/图/式；文字或转述来源无原生锚点时不得虚构 |
| 作用范围 | 判断其针对单句、段落、整节步骤、公式节、整张图或跨章节组合，并写依据；不确定时填“范围待用户确认” |

代理人说“第五章那个公式 2”时，操作者写入 `EQ:2` 是一次人工翻译。门禁只能证明 `EQ:2` 可解析，不能证明翻译正确。因此，首次建立机器锚点时必须把“代理原话 → 人类可读位置 → 机器锚点”并列给人工确认；fallback 命中不能作为干净 PASS。

## R3 生成正文内嵌标注版

以正文真源 MD 为底稿，在对应位置插入：

```html
<!-- REVIEW_COMMENT_BEGIN id="C01" source_native_id="0" author="{作者}" target="{锚定对象}" -->
**【代理意见 C01｜原文】**

~~~~text
{原文，逐字}
~~~~
<!-- REVIEW_COMMENT_END id="C01" -->
```

落盘为 `{案件名}_代理批注定位版_{YYYYMMDDHHmmss}_{producer}.md`。文首说明外部意见不得并入正文，并附 R2 定位索引。

生成前做双真源核对：审阅 DOCX 是审阅真源，本地 MD 是正文真源。技术正文不一致时记录差异，以审阅正文为修订基准或先回写 MD；未经核对不得宣称二者同源。

## R4 逐条分诊

按 `correction_handler.md` 将每条意见内部标为 `采纳 / 拒绝（附证据）/ 存疑`。

- “具体体现在何处”：先找正文中的步骤、公式和实施例支撑。找不到时只能补全正文或降级/删除保护点，不能只在保护点旁补一句。
- “以哪个为准”：回到统一方案骨架，对齐正文、图、公式、实施例、保护点和 MVP，不能只改一个视图。
- 一条意见含多个独立要求：保留一个顶层编号，在理解、具体处理和联动检查中用 `C01.1 / C01.2 …` 逐项闭环；C14 仍按一条顶层意见计数。

## R5 修订落地与处置矩阵

按 `correction_handler.md` 另存新时间戳 MD/DOCX并完成自检。多 Agent 并行时文件名追加 producer；旧稿与其他 Agent 成果保留，由用户选择。

在案件目录落盘或追加 `批注处置矩阵.md`：

| 批注编号 | 代理意见原文 | 意见理解 | 内部判断 | 对外状态 | 修改说明 | 人类可读位置 | 机器锚点 | 是否影响 MVP/计算 | 联动检查 | 最终状态 |
|---|---|---|---|---|---|---|---|---|---|---|
| C01 | {逐字原文} | {含子要求编号} | 采纳/拒绝/存疑 | 已落实/部分落实/待补充材料后落实/暂未落实 | {实际动作或原因} | 第三章步骤 S4 | `STEP:S4; FIG:2; KP:3` | 是/否/待判断 | 正文；图；公式；实施例；保护点；查新；MVP | CLOSED/PARTIAL/OPEN |

关键规则：

- 原文不可摘要、改写、合并或润色；“意见理解”才用于概括。
- 正式回复只用四种对外状态，不直接写“拒绝/不采纳”。
- 人类可读位置给代理人，机器锚点给 C16/C17；工具不得从自然语言位置猜锚点。
- MVP 影响为“是”时至少登记一个 `MVP:`，并核对实际计算/测试。
- `PARTIAL/OPEN` 必须列明残留和下一步。

### 机器锚点

| 类型 | 语法 | 示例 |
|---|---|---|
| 技术步骤 | `STEP:<编号>` | `STEP:S4` |
| 决策节点 | `DECISION:<编号>` | `DECISION:D3` |
| 公式 | `EQ:<编号>` | `EQ:2` |
| 附图 | `FIG:<编号>` | `FIG:2` |
| 保护点 | `KP:<编号>` | `KP:3` |
| 章节 | `SECTION:<编号或稳定ID>` | `SECTION:3.2` |
| MVP/测试 | `MVP:<相对路径>` | `MVP:tools/model.py` |
| 普通文件 | `FILE:<相对路径>` | `FILE:notes.md` |
| 删除目标 | `DELETE:<目标锚点>` | `DELETE:KP:3` |

多个锚点用半角分号。删除对象必须用 `DELETE:`。`已落实/部分落实` 原则上至少有一个锚点；“确认事实且无需改稿”等豁免必须写客观原因。

## R6 逐条回复与门禁

按 `templates/attorney_response_matrix.md` 生成 `代理意见回复_{YYYYMMDDHHmmss}_{producer}.md`。每条固定顺序：

代理意见原文 → 意见理解 → 处理结果 → 具体处理 → 人类可读位置 → 机器锚点 → 联动影响 → 尚待确认。

门禁参数：

```text
--comments-json "{原文包.json}" --attorney-reply "{代理回复.md}" --revision-matrix "{批注处置矩阵.md}" --revision-root "{修订根目录}" --baseline-md "{基线.md}" --baseline-root "{基线根目录}"
```

- C14：顶层条数少一条即 FAIL；条数为 provisional 时 WARN，取得用户确认前不得称完整覆盖。
- C16：只检查锚点语法与对象存在。fallback 命中只能 WARN；人工还须确认“对象确为代理人所指对象”。
- C17：只检查声称修改处有可识别 diff，不证明语义上已解决意见。无基线时 WARN；C16 失败时记 `not_evaluated`，不得显示 PASS。
- 正式外发版可隐藏机器锚点，但门禁工作底稿或处置矩阵必须保留。

## R7 经验回写与 Skill 吸收候选

按 `templates/attorney_revision_lessons.md` 生成 `代理意见经验回写_{YYYYMMDDHHmmss}_{producer}.md`。每轮至少回答：

1. 哪些是本案事实，不能泛化；
2. 哪些是可复用的写作/流程规则；
3. 哪些可转为确定性工具或回归测试；
4. 哪些只是风险猜测、尚无事故证据；
5. 本轮已吸收到哪个 prompt、tool、test 或案件记录。

经验回写是案件留档，不自动发布到公共仓库。只有去标识化、复核通过且有失败夹具或证据的通用条目才进入 Skill。无法自动化的专业判断保留为人工检查，不为了增加门禁而强写正则。

## 输出摘要

交付时输出“批注闭环摘要（留档）”：来源类型与原文状态、顶层意见数及条数是否确认、内部三态、对外四态、CLOSED/PARTIAL/OPEN 数量、新稿、回复稿与经验回写文件名。

## 禁止

- 把代理意见并入交底书正文。
- 把无锚点扁平清单作为唯一提取结果。
- 点批注不判断作用范围；文字来源虚构 Word 落点。
- 正文无支撑时只在保护点旁补解释。
- 对外声称与实际修订、查新证据或数值证据不一致。
- 把 C16/C17 的 PASS 当作“意见语义已解决”。
